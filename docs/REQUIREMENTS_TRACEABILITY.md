# 老师需求对照与 v2 验收说明

本文以当前正式架构为准：`miniprogram/` 是原生微信小程序 v2 主线，`backend/` 是唯一业务后端。`frontend/` 和 `cloudfunctions/` 仅作参考，不能用它们的页面或接口证明正式 v2 已完成。

状态含义：

- **已接入**：原生页面与 FastAPI 已形成调用链，可做本地业务验收。
- **后端具备**：FastAPI 已有能力，但原生页面尚无完整入口。
- **待平台配置**：代码链路存在，必须取得微信/学校正式资源后才能真机验收。
- **未接入**：当前只有限制说明或占位，不应宣称功能完成。
- **待学校决定**：身份/业务/隐私等需要学校确认，不自行推断实现。
- **已编写/已实现**：教程/工具已准备，本地证据另列，不代表真人或学校环境验收。

## 需求解释

1. 老师材料前文称 B102 为音乐专属房间，后文又允许使用 A103 钢琴。v2 统一解释为“B102 优先、A103 钢琴作为第二候选”，且不撤销已经成立的预约。
2. A103 的大型活动和音乐练习共用同一物理房间，因此按重叠时段互斥；B102 不应被错误联锁。
3. 姓名、学号、手机号来自登录账号，预约时不重复填写；管理员审核和授权导出仍可查看。
4. 房间详情只展示占用时段，不恢复第一版公开显示预约人姓名、班级和理由的做法，避免不必要的信息暴露。
5. “保留 V1 体验”指空间导览、双页预约、连续时段、我的预约等产品骨架；当前正式视觉为暖橙+紫色，第一版云函数、信用分、公开预约人详情和短信占位实现不进入正式 v2。

## 自动化验收基线（#12、#21、#22）

- 后端业务不再集中在 `services.py`：预约、审核、限制、媒体、房间、设置和用户分别归属 `backend/app/domain/`；旧文件只保留兼容导出，约定测试会阻止再次膨胀。
- 原生管理页把标签路由、展示映射、审核/限制/设置/分房表单规则拆入独立模块，页面入口只负责微信交互和请求编排；这些模块可由 Node 测试单独加载。
- 小程序 CI 回归覆盖登录恢复、并发 401、连续时段与共同房间、上传后的预约/清扫提交、管理员审核及管理配置规则。
- 后端自动化覆盖管理员权限矩阵、跨用户越权、停用账号旧令牌、取消/签到时间边界、状态推进幂等及微信 outbox 的 HTTP/业务失败重试。
- PostgreSQL CI 除真实行锁防重复预约外，还校验后台任务 advisory lock 只允许一个 leader。
- SQLite 本地测试用于快速反馈；SQLite不能证明行锁；PostgreSQL并发CI、初始化容器与恢复容器演练分别记录，不能互相替代。
