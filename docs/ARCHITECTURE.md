# 系统架构与审查结论

## 审查结论

原仓库有两套并行实现：FastAPI/uni-app 与原生小程序/微信云函数。两套数据模型、状态和校验规则不同，云函数还把配置硬编码在多个文件中，因此会出现同一规则在不同端结果不一致、云环境到期后无法运行的问题。v2 选择仓库既定的 FastAPI + uni-app 为唯一主线；旧目录保留，但不参与运行。

原实现的主要风险及 v2 处理如下：

| 风险 | v2 处理 |
|---|---|
| 只有整点时段 | 统一用 `start_slot/end_slot` 表示半小时区间，结束值为开区间 |
| 先查再写，高并发可重复预约 | PostgreSQL 事务中锁定候选房间规则；A103/B102 先按固定顺序同时加锁 |
| 只有 active/cancelled/check-in 状态 | 完整状态机覆盖待审核、通过、使用、清扫复核、完成/驳回 |
| 房间规则写死在前后端 | `room_scene_rules` + `system_settings`，后台直接修改 |
| “每天只能一单”误代替 4 小时累计 | 对所有占用状态按 slot 累加分钟数 |
| 没有清扫闭环 | 独立核验表；未通过或待复核时服务端阻断新预约 |
| 封禁只有一个日期 | 独立限制记录，支持临时、限时、永久、原因与撤销审计 |
| 消息发送失败影响业务或直接丢失 | 与业务同事务写入 outbox，后台任务异步重试 |
| CORS 全开放、密钥有弱默认值 | CORS 白名单和 `.env`；生产必须替换 `SECRET_KEY` |

## 分层

```text
uni-app（微信小程序 / H5）
        │ HTTPS + JWT
        ▼
FastAPI routers（鉴权、参数、HTTP 响应）
        ▼
services.py（分房、冲突、审批、清扫、限制，事务边界）
        ▼
SQLAlchemy async ── PostgreSQL（生产）/ SQLite（演示）
        │
        └── Notification outbox ── 定时任务 ── 微信订阅消息 API
```

前端只负责采集场景、时段、人数、用途和展示结果，不能指定最终房间，也不承担安全校验。后端按数据库中的规则分房，并再次执行所有权限、时长、资格和冲突校验。

## 核心数据表

| 表 | 关键字段与用途 |
|---|---|
| `users` | 学号、角色、密码摘要、微信 openid、启用状态 |
| `rooms` | 房间基础信息、物理容量、公开状态 |
| `room_scene_rules` | 场景、房间、优先级、场景容量、共享/独占、启用状态 |
| `reservations` | 场景、自动分配房间、日期、slot 区间、人数、用途、完整状态与审核信息 |
| `cleanup_verifications` | 多张照片 URL、提交/复核状态、备注与复核人 |
| `booking_restrictions` | 临时/限时/永久、起止时间、原因、创建人、撤销状态 |
| `system_settings` | 开放时间、时长上限、自动审批时刻等 JSON 标量配置 |
| `notifications` | 消息类型、载荷、计划时间、发送状态、重试次数与错误 |

## 分房与冲突规则

- 自习：A102 → A101 → A105，按规则容量共享。
- 开会：A105 → A101 → A102，独占。
- 大型活动：仅 A103，独占。
- 音乐练习：仅 B102，独占。
- A103/B102 在重叠时段互斥。大型活动提交时会释放尚未开始的冲突音乐预约并发送结果通知。
- 待审核申请也占用容量，避免管理员审核前被超卖。
- 每日时长统计包含待审核、已通过、使用中、待清扫等有效占用状态；取消/驳回不计入。

## 状态流

```text
pending ──审核/23:00──> approved ──签到──> in_use ──到时──> cleanup_pending
   │                       │                                      │
   ├── rejected            ├── missed                             ├── completed
   └── cancelled           └── cancelled                          └── cleanup_rejected ──重传──> cleanup_pending
```

`cleanup_pending` 同时表示“等待上传”或“已上传等待复核”，是否已有核验记录由 `cleanup` 字段区分。任一 `cleanup_pending/cleanup_rejected` 会阻断该学生新建预约。

## 定时任务

每分钟执行一次轻量 tick：

1. 推进超时预约状态；
2. 到后台配置的时刻（默认 23:00）自动通过全部待审核单；
3. 投递到期的提交、审核、临近开始、封禁订阅消息。

内置调度器适合单实例交付。学校若横向扩容，应只保留一个任务实例，或改用学校 cron/任务平台。
